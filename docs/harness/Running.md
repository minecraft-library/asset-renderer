# Running the harness

Load when choosing or wiring a run mode, reading what a run writes, or diagnosing a run that hangs
with no output or halts with exit 4. Every mode is here in full, the whole-tree run included; the
world reset is in [`harness/CLAUDE.md`](../../harness/CLAUDE.md).

- Full sweep (blocks + items + entities + the player): `./gradlew runRenderReferences [-PrefharnessTargets=ns:id,...]` from `harness/`, or `./gradlew renderVanillaReferences` from asset-renderer (output → asset-renderer's cache). **Not the whole tree** - it leaves `glint/`, `armor/`, `menus/`, `tooltips/`, `idle/` and `walk/` alone.
- Whole tree in one boot - **run this after any change to a frame renderer**: `./gradlew renderVanillaAllReferences` from asset-renderer, which passes `-PrefharnessModes=EVERY,ANIMATION,WALK`. Every sweep in one client launch, measured at **1m 25s** for the whole tree - it pays the boot once, and every large sub-tree renders at the pacing cap of 8 subjects a tick. The narrow modes below stay for scoped iteration; relying on them is what left stale ground truth on disk twice. **The whole-tree render reproduces, measured rather than assumed**: two boots seven hours and 26 perturbation cycles apart hashed the same tree, and every sweep digest the parity store holds rests on that.
- **A boot holds no lane of the asset build.** Every asset-renderer harness run hands its boot to the Worker API, so the project's other tasks run while the client renders - in a capture, the producers that read nothing of the tree overlap it. What reads what a run draws waits for it: the sweeps and the capture steps off the tree their rows read, the slow suite and the schedule check off the reference tree, the toolkit's suite off every run, and each probe report off its own probe. And one client boots at a time, every run and the harness compile leasing the same `harnessClient` service, because every boot shares one run directory and one world save.
- **`references-rendered.json` beside the tree records the last whole render.** `renderVanillaAllReferences` with no `-PrefharnessTargets` digests what it is about to read beside the schedule roster - the trigger paths of every rule that boots the tree - into `references-rendered.pending.json` before it boots, and renames it to the record once the boot exits 0. Every asset-renderer run that writes into the tree deletes the record before it boots, a targeted whole-tree run included, so the record stands only over a tree whose last write was a whole boot that finished. A capture's schedule check refuses to skip the boot without it. A run started from `harness/` and pointed at the tree with `-PrefharnessOutputDir` goes through none of this and leaves the record standing, so a tree written that way is refreshed with `renderVanillaAllReferences` before the next gate.
- Glint-only (fast, decoupled): `./gradlew runRenderReferences -PrefharnessModes=GLINT`, or `./gradlew renderVanillaGlintReferences` from asset-renderer.
- Animated-only: `./gradlew runRenderReferences -PrefharnessModes=ANIMATION`, or `./gradlew renderVanillaAnimationReferences` from asset-renderer. Every type's default, its baby and the posed trait subjects the roster names, each at the frames its schedule names, into `idle/<subject>/frame_NNN.png`. **Both posed modes read `entity-schedule/roster.json` beside the output root and refuse without it** - asset-renderer's `entityScheduleRoster` writes it, and its three posed tasks run that first - so posed references are made from asset-renderer; a run from `harness/` with no `-PrefharnessOutputDir` finds no roster beside `harness/build/refharness-output` and stops before any sweep.
- Walk-only: `./gradlew runRenderReferences -PrefharnessModes=WALK`, or `./gradlew renderVanillaWalkReferences` from asset-renderer. The same subjects, each at its walk schedule, into `walk/<subject>/frame_NNN.png`, the stride armed at the walk speed and walk-clock rate the roster names; the same roster, read the same way. These two and the whole-tree run are the only ones whose client draws a posed subject; every other one, no mode naming a posed one, is bit-for-bit what it always was - measured, not asserted: adding the gait re-rendered `idle/` byte-identical on all 720 frames.
- Armor-only (fast, decoupled): `./gradlew runRenderReferences -PrefharnessModes=ARMOR`, or `./gradlew renderVanillaArmorReferences` from asset-renderer. `ArmorSweep` renders a fixed roster of **armored** mobs, adult and baby (zombie / piglin, iron and dyed leather). The main entity sweep puts iron on its humanoid adults, a saddle or a body item on each model that wears one and the elytra on the wearers `EntityRoster` selects it for, and it draws the baby of every type vanilla gives one - but it puts armour on no baby and dyes no humanoid leather, so vanilla's separate baby armour mesh and dyed humanoid leather have ground truth only here, with the adults as their controls. Diagnostic, not a byte-stable reference set: each subject is fit to 80% of a square canvas so the armor shell stays inside the frame regardless of what was measured, and the consuming diff crops and aligns by silhouette. (The bounds walker reads an armour layer's meshes out of its `ArmorModelSet`, but `isLayerActiveForState` walks the layer only for a reference whose request selects the `equip` or `armor` axis, and `ArmorSweep` sets no request - so on its subjects the walker measures the body alone, and the reserved margin is the only thing keeping the shell in frame.)
- Tooltips-only: `./gradlew runRenderReferences -PrefharnessModes=TOOLTIPS`, or `./gradlew renderVanillaTooltipReferences` from asset-renderer. Every subject of the tracked tooltip roster drawn through the client's own tooltip call into `tooltips/<key>.png`, and its box alone into `tooltips/<key>_chrome.png`, and every plain line through the hotbar name's text draw into `tooltips/plain/<key>.png`. Like every reference mode it is named through the modes list. The roster is read by path from `refharness.tooltipRoster`, which the harness build sets on every run, defaulting it to asset-renderer's `src/visual/resources/lib/minecraft/renderer/sweep/tooltip-roster.json`. Another file is drawn only from `harness/`, with `./gradlew runRenderReferences -PrefharnessModes=TOOLTIPS -PrefharnessTooltipRoster=<path>`: the asset-renderer task forwards no roster property, so it always draws the tracked one. The capture, and what the sweep asserts before it draws, are [GuiCapture](GuiCapture.md).
- Output dirs under the output root: `blocks/`, `entities/`, `items/`, `players/`, `glint/` (+ `glint/atlas_uv.json`), `armor/`, `menus/`, `tooltips/`, `idle/` and `walk/` (+ each one's `schedule.json`, the schedule every stem was rendered at). Beside the tree: `entity-schedule/roster.json`, which the posed modes read, and `references-rendered.json`, the record of the last whole render.
- **World creation fires on the first screen that is not a loading step.** `WorldBootstrap` skips `LevelLoadingScreen`, `ProgressScreen`, `GenericMessageScreen` and `GenericWaitingScreen` and takes over on anything else. Keying on `TitleScreen` alone hung the run with no error and no output whenever the client settled somewhere else first, and the first-run accessibility onboarding is the screen that has actually done it. The accepted risk is the mirror image - firing on a screen the client is not ready to leave. If `createFreshLevel` throws, the catch resets the one-shot and the next settled screen retries; if it neither throws nor produces a level, the watchdog is what ends the run. `RefHarnessClient` halts with exit **4** once 3600 consecutive client ticks have passed with no level or no player, printing the last screen the hook saw and whether creation ever fired - the two facts that say which of the two happened. The count starts at the first tick after the mod initialises and the client ticks at twenty a second throughout the resource reload, so those three minutes are boot **plus** the wait, not three minutes of waiting alone; a machine that takes longer than that to reach a screen trips it. A level and a player together reset the count to zero. **Neither half is under a test, and nothing in the harness build is** - it has `main` and `client` source sets and no test one, so a change here is caught by the compiler or by an actual run and by nothing in between. Measured: narrowing the skip list to `LevelLoadingScreen` alone, inverting the guard so no world is ever created, and setting the timeout to one tick or to unreachable each compile clean and each leaves asset-renderer's `./gradlew test` green. Renaming a screen class or dropping `hasScheduled()` is caught, because that is a symbol the compiler resolves. Change one of these and run the sweep.
