# Capturing a GUI

Load when touching `GuiFrameRenderer`, `GuiTarget`, `MenuSweep`, `TooltipSweep`, `BookSweep`,
`BookViewScreenAccessor`, or one of the mixins a capture arms - `GuiRenderTargetMixin`,
`SuppressScreenBackdropMixin`, `FreezeTextCursorMixin`. Indexed from
[`harness/CLAUDE.md`](../../harness/CLAUDE.md).

`GuiFrameRenderer` is the one capture that submits no geometry. A GUI subject is worth comparing against only as the client composes it - a menu's panel, its two labels and its slots through vanilla's own GUI item atlas, a tooltip's box and the text over it, a book's page and the text on it - so the capture drives vanilla's own extract-then-draw and changes only where the draw lands. Each GUI sweep hands it an extract step, which is the whole of what differs between them; the window swap, the redirect, the clear, the draw and the read-back are the capture's own, written once for all three.

- **`GuiRenderer` cannot be redirected the way everything else here is.** It resolves `Minecraft.getMainRenderTarget()` at one call site inside its private `draw` and never reads `RenderSystem.outputColorTextureOverride`, which is what `PipTarget` sets and what every other offscreen render depends on - a grep of the extracted client finds exactly four classes holding that field (`GuiItemAtlas`, `PictureInPictureRenderer`, `LevelRenderer`, `RenderType`) and `GuiRenderer` is not one. `GuiRenderTargetMixin` swaps the target at that call site instead, reading `GuiTarget.override`, which is the `GlintClock` pattern: a plain holder the capture arms and clears so the redirect is inert for every frame that is not being captured. It needs a real `RenderTarget` (a `TextureTarget`), not a `GpuTextureView`.
- `GameRenderer.guiRenderer` and `.fogRenderer` are private with no getters; `GameRendererAccessor` opens both. The draw is `guiRenderer.render(fogRenderer.getBuffer(FogMode.NONE))`.
- Three pieces of global state move for the duration and go back in a `finally`: `windowRenderState.{width, height, guiScale}` (the GUI projection is built from these, so they are what puts the subject on the canvas at one Minecraft pixel per `GUI_SCALE`), the `GuiRenderState` the extract fills, and the target. The extract step runs with all three moved and the redirect armed. The extractor is built with `mouseX = mouseY = -1`, so nothing a step extracts is hovered - for a menu that neutralises the slot highlight and the slot tooltip together, being one test in vanilla rather than two.
- The read-back is `pip/TextureReadback`, shared with `PipTarget` rather than copied. It takes the extent as parameters because the copy's callback runs a frame later, by which time the target that owns the texture may have resized - passing them in is what makes handing it a field that is re-read later unrepresentable. A PNG write that fails after that callback - the encode runs on the read-back's own pool, which the exit hook waits out - is logged with its path and counted, and the run's exit status reads the count, so a write that failed after its copy landed cannot leave the previous run's file standing behind a run that exits 0.
- Each GUI sweep owns its own capture, which reuses its target while the canvas keeps its size and destroys a replaced one on the spot, as vanilla's own `PictureInPictureRenderer` closes its textures on a resize. The read-back's copy is issued into the command stream before `copyTextureToBuffer` returns, and only the buffer's mapping and the PNG write wait behind a fence, so a destroy that follows is behind the copy it would otherwise race.

## Menus

- **The panel is the background half of a screen's state, and the caller is what draws it.** `AbstractContainerScreen.extractRenderState` calls only `extractContents` / `extractCarriedItem` / `extractSnapbackItem` / `extractTooltip` - that yields the labels and the slots and no panel at all. The blit lives in each screen's own `extractBackground` override, so the menu's extract step calls **both** entry points, background first.
- That override reaches its blit through `super`, so the base `Screen.extractBackground` runs first and, with a level loaded, draws the blurred world plus a dark tint behind the panel. `SuppressScreenBackdropMixin` cancels the base only - the cancel returns from `Screen`'s own body and the subclass's blits are untouched - and is gated on a capture being armed as well as on headless, which is why the capture arms the redirect before the extract step rather than just before the draw.
- `screen.init(w, h)` at the panel's own size is what makes `leftPos == topPos == 0`. It is the first thing the menu's extract step does, inside the window swap.
- **A subject's state lives on the widgets `init` builds and, for the anvil, on the menu `init` makes the screen a slot listener of, so a subject that has something to say says it in `MenuSubject.afterInit`** - after `screen.init` and before the extract, the one window in which a widget both exists and has not been read, and in which the screen hears of a slot its menu fills as the client's screen does. Six anvils use it. The named one and the highlight one set a name whole, through the field's own `setValue` - the call the screen names the field through when an item is placed - rather than typing it: `AnvilScreen.name` is private, `AnvilScreenAccessor` opens it, and the responder is dropped before the value is set because the screen's own sends a rename packet per change. Every other route to that text moves something else too - a named item in the input slot fills the slot and flips the field to its enabled sprite - so two subjects would differ in three ways rather than in the one being measured. The other four fill the slots instead, below.
- **A filled anvil is filled through its own menu, its result last.** `MenuSweep.holdItems` sets each input through its slot, and the menu answers as it does in play: `ItemCombinerMenu.slotsChanged` reports every changed slot to its listeners through `broadcastChanges`, then runs `createResult`. The screen is that listener, so the report on the first input is its own `slotChanged`, which names the field after the item placed and makes it editable - the field the client then draws enabled. The responder is dropped before the first set, because naming the field would otherwise rename through the menu, run `createResult` again and send a packet. Every input set runs `createResult`, which makes no result for these inputs, so the result goes in last; its own set is reported and runs nothing, the menu recomputing for its input container alone. The cost stays 0 on `createResult`'s own paths - an empty first input, a repair material against an undamaged first input, and a first input alone with nothing to repair or combine and no name the menu was told of - so the screen draws no cost label. A result standing at a cost of 0 is a state the menu's own rules never produce, kept because it measures the field, the cross and the cells and no renderer option draws a cost. `anvil_result` holds both inputs and the sword as its result (the enabled field, no cross), `anvil_error` the diamond alone in the second input (the disabled field and the cross), and `anvil_input` the sword alone in the first (the enabled field and the cross); with the empty `anvil` they tell apart every condition the screen picks its field and draws its cross by. `anvil_apple` holds the enchanted golden apple alone in the first input, as `anvil_input` holds the sword, so the screen's own `slotChanged` names the field after it - a name too wide for the field, which is what the subject measures.
- **A focused text field blinks on the wall clock, so it is pinned.** `TextCursorUtils.isCursorVisible` is `(millis-since-focus / 300) % 2 == 0`, and the anvil focuses its field during `init`; the capture draws immediately after, so the caret is visible on every ordinary run and a 300 ms stall anywhere between the two would blink it out and move the reference by the ten pixels it paints. `FreezeTextCursorMixin` pins it visible - the same freeze `FreezeSpriteAnimationMixin` applies to texture animation, and visible rather than hidden because a freeze holds what the client draws still rather than deciding what it draws.
- The caret has **two forms and the value's length picks which**: vanilla appends a `_` glyph, drawn with a shadow where `EditBox` leaves its pen - at the text origin in an empty field, and a pixel past the text's `Font.width` after any, the widget stepping its pen past what it draws - unless the cursor is at the end of a value already at its maximum length, when it steps back that pixel and fills a one-pixel bar spanning eleven rows on the text's own end instead. The anvil caps its field at 50, so the two empty subjects draw the first at the origin, the three holding a placed item's name draw it after their text, and a subject named at that cap draws the second - which is why the named one is at exactly fifty characters and not at a comfortable length. Both forms are drawn only while the cursor is in view: where the field's scroll leaves it out of view, the client draws no caret and adds a blue highlight band from a pixel inside the shown text's end to the field's right edge, which `anvil_highlight` is named for.
- **A field set whole scrolls three times.** `EditBox.setValue` scrolls a fresh field toward the cursor at the text's end once placing the cursor, once placing its highlight with it, and once more placing the highlight again, each pass moving the field's start forward by as many characters as were left past the end of the head it showed; the field then shows the head of what is left that fits. Placing an item names the field this way, which is why `anvil_apple` shows `anted Golden Apple` rather than `hanted Golden Apple`, the widest tail that fits. Typing scrolls by other steps, two passes a keystroke from wherever the last one left the field. `anvil_highlight`'s `lil' MAMMOTH WARHAMMER` leaves the cursor out of view after the third pass, where two would show other text and four would bring it into view.

## Tooltips

- **The call is the client's own `tooltip(...)`, at a fixed origin.** `TooltipSweep`'s extract step is `GuiGraphicsExtractor#tooltip` over the subject's lines as the client's own tooltip components, never the item route, which adds attribute and advanced lines the roster did not ask for. Its positioner places the box at the content origin it is handed, GUI `(12, 12)`: the client's default positioner measures against `guiWidth()`, which reads the hidden window rather than the capture's swapped extent, so it would flip or clamp a wide line against a window nobody sees.
- **The canvas is the whole sprite rect.** The width and height are the client's own measurement, the loop `tooltip(...)` itself runs - the widest line, and every line's height summed less two for a one-line tooltip - and both tooltip sprites are blitted 12 GUI pixels outside that on every side, so the canvas is the measurement plus 24 each way at `GUI_SCALE` and nothing the client draws for a tooltip falls off it.
- **Every tooltip subject has a box-alone twin**, `<key>_chrome`, drawn through `TooltipRenderUtil.extractTooltipBackground` at the same measurement: a mover in the twin is the box, and one in the full tooltip alone is the text. The two are drawn in that order at one canvas size, so a pair costs one resize.
- **A plain line is the hotbar's drawing of an item's name.** The roster's plain section is drawn by the text draw `Gui#extractSelectedItemName` reaches through `textWithBackdrop` - the line and its shadow, opaque white where it names no colour - into `tooltips/plain/<key>.png`, at the same fixed origin, on the client's width of the line and the font's line height plus 12 GUI px a side. The call fills a backdrop first only where the text background is not for chat only, which it is by default, so the sweep draws the text alone rather than asserting the option. A plain line has no box and no twin, and a pack run draws no plain line.
- **The client's options and packs are the run's to assert**: before its first sweep a run refuses a client at high contrast, with the forced Unicode font or the Japanese glyph variants on, in a language other than `en_us`, or with the built-in high-contrast or programmer-art pack selected ([SweepArchitecture](SweepArchitecture.md)) - the high-contrast pack replaces both tooltip sprites, and programmer art the block, item, entity and GUI textures the other sweeps draw. A font option and a pack take effect through a resource reload and the run directory is shared, so the run refuses such a client rather than changing it. A pack run's tooltip sweep refuses one thing more: a pack it requested that the client did not select.
- **The roster is read by path and parsed by the client's own codec.** `refharness.tooltipRoster` names it, and the harness build defaults that to asset-renderer's tracked `src/visual/resources/lib/minecraft/renderer/sweep/tooltip-roster.json`. Each line is a text component parsed by `ComponentSerialization.CODEC` against the running registries; a line the codec refuses, a roster of another format or two subjects that would write one file refuses the run before its first PNG.
- **A pack run is the same sweep and the same capture** over the roster's section for its packs: `TooltipSweep` constructed for a pack run draws that section into `pack-tooltips/<label>/` beside the reference tree, its sprite ids read through the client's own style-to-sprite helpers. The run, its handshake and the rule its lines keep are in [Probes](Probes.md).
- **No subject is obfuscated.** The client picks an obfuscated glyph off `Font.random`, which nothing seeds, so such a reference would not reproduce and the whole tree's determinism would go with it.

## Books

- **The screen is the client's own, opened over a book of the one page.** `BookSweep` builds `new BookViewScreen(new BookViewScreen.BookAccess(List.of(page)))` - both public, the access a record over the page list - and never makes it the client's screen, as the menu sweep never does; the subject naming no page opens the client's own empty book. The page is a text component parsed by `ComponentSerialization.CODEC` against the running registries, the tooltip roster's parse; a page the codec refuses, a roster of another format or two subjects that would write one file refuses the run before its first PNG.
- **`init` at the book's own width puts the book at the canvas edge, two rows down.** `screen.init(192, 194)` makes `backgroundLeft()` 0, and `backgroundTop()` is the client's constant 2, so the canvas is the screen at that extent, 384 x 388 at `GUI_SCALE`, and the two GUI rows above the book are clear in every reference: the capture keeps the client's placement rather than moving the pose, an op the client's frame does not have. Every page is one canvas size, so the book's capture allocates its target once.
- **The extract step is the client's frame with one call replaced.** `Screen`'s frame opens a stratum, extracts the background, opens a stratum, extracts the screen's state and extracts the deferred elements; the book's step makes the same calls in the same order, with the screen's private `visitText`, called through `BookViewScreenAccessor` with its click-only flag set, in place of the state. The visit reads that flag at one place, the jump over the "Page N of M" line, so the page cache, the split at 114 GUI px, the fourteen-line cap and every line's position run as the screen's own frame runs them and the page number is not drawn. The state extract is never called, so no widget is: on a one-page book the client hides both arrows itself, and Done sits at GUI y 196, below the canvas. The collector is the one the screen's own state builds, `textRenderer(TOOLTIP_AND_CURSOR)`, and with the mouse at `-1` it hovers nothing, so the deferred elements draw nothing.
- **The background alone is the twin every page shares.** The book's background is one 192 x 192 blit whatever the page holds, so one subject, `background`, draws it alone - the frame without its text visit - where the tooltip sweep gives every subject a twin: a mover there is the book's texture, and a mover in a page alone is its text. `empty`, the whole frame over an empty page, draws the same pixels.
- **No page is obfuscated**, for the tooltips' reason: the client picks an obfuscated glyph off `Font.random`, which nothing seeds.
