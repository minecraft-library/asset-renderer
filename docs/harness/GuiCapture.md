# Capturing a GUI

Load when touching `GuiFrameRenderer`, `GuiTarget`, `MenuSweep`, `TooltipSweep`, or one of the
mixins a capture arms - `GuiRenderTargetMixin`, `SuppressScreenBackdropMixin`,
`FreezeTextCursorMixin`. Indexed from [`harness/CLAUDE.md`](../../harness/CLAUDE.md).

`GuiFrameRenderer` is the one capture that submits no geometry. A GUI subject is worth comparing against only as the client composes it - a menu's panel, its two labels and its slots through vanilla's own GUI item atlas, a tooltip's box and the text over it - so the capture drives vanilla's own extract-then-draw and changes only where the draw lands. Each GUI sweep hands it an extract step, which is the whole of what differs between them; the window swap, the redirect, the clear, the draw and the read-back are the capture's own, written once for both.

- **`GuiRenderer` cannot be redirected the way everything else here is.** It resolves `Minecraft.getMainRenderTarget()` at one call site inside its private `draw` and never reads `RenderSystem.outputColorTextureOverride`, which is what `PipTarget` sets and what every other offscreen render depends on - a grep of the extracted client finds exactly four classes holding that field (`GuiItemAtlas`, `PictureInPictureRenderer`, `LevelRenderer`, `RenderType`) and `GuiRenderer` is not one. `GuiRenderTargetMixin` swaps the target at that call site instead, reading `GuiTarget.override`, which is the `GlintClock` pattern: a plain holder the capture arms and clears so the redirect is inert for every frame that is not being captured. It needs a real `RenderTarget` (a `TextureTarget`), not a `GpuTextureView`.
- `GameRenderer.guiRenderer` and `.fogRenderer` are private with no getters; `GameRendererAccessor` opens both. The draw is `guiRenderer.render(fogRenderer.getBuffer(FogMode.NONE))`.
- Three pieces of global state move for the duration and go back in a `finally`: `windowRenderState.{width, height, guiScale}` (the GUI projection is built from these, so they are what puts the subject on the canvas at one Minecraft pixel per `GUI_SCALE`), the `GuiRenderState` the extract fills, and the target. The extract step runs with all three moved and the redirect armed. The extractor is built with `mouseX = mouseY = -1`, so nothing a step extracts is hovered - for a menu that neutralises the slot highlight and the slot tooltip together, being one test in vanilla rather than two.
- The read-back is `pip/TextureReadback`, shared with `PipTarget` rather than copied. It takes the extent as parameters because the copy's callback runs a frame later, by which time the target that owns the texture may have resized - passing them in is what makes handing it a field that is re-read later unrepresentable. A PNG write that fails inside that callback is logged with its path and counted, and the run's exit status reads the count, so a write that failed after its copy landed cannot leave the previous run's file standing behind a run that exits 0.
- Each GUI sweep owns its own capture, which reuses its target while the canvas keeps its size and destroys a replaced one on the spot, as vanilla's own `PictureInPictureRenderer` closes its textures on a resize. The read-back's copy is issued into the command stream before `copyTextureToBuffer` returns, and only the buffer's mapping and the PNG write wait behind a fence, so a destroy that follows is behind the copy it would otherwise race.

## Menus

- **The panel is the background half of a screen's state, and the caller is what draws it.** `AbstractContainerScreen.extractRenderState` calls only `extractContents` / `extractCarriedItem` / `extractSnapbackItem` / `extractTooltip` - that yields the labels and the slots and no panel at all. The blit lives in each screen's own `extractBackground` override, so the menu's extract step calls **both** entry points, background first.
- That override reaches its blit through `super`, so the base `Screen.extractBackground` runs first and, with a level loaded, draws the blurred world plus a dark tint behind the panel. `SuppressScreenBackdropMixin` cancels the base only - the cancel returns from `Screen`'s own body and the subclass's blits are untouched - and is gated on a capture being armed as well as on headless, which is why the capture arms the redirect before the extract step rather than just before the draw.
- `screen.init(w, h)` at the panel's own size is what makes `leftPos == topPos == 0`. It is the first thing the menu's extract step does, inside the window swap.
- **A subject's state lives on widgets `init` builds, so a subject that has something to say says it in `MenuSubject.afterInit`** - after `screen.init` and before the extract, the one window in which a widget both exists and has not been read. The named anvil is the only user: `AnvilScreen.name` is private, `AnvilScreenAccessor` opens it, and the responder is dropped before the value is set because the screen's own sends a rename packet per change. Every other route to that text moves something else too - a named item in the input slot fills the slot and flips the field to its enabled sprite - so two subjects would differ in three ways rather than in the one being measured.
- **A focused text field blinks on the wall clock, so it is pinned.** `TextCursorUtils.isCursorVisible` is `(millis-since-focus / 300) % 2 == 0`, and the anvil focuses its field during `init`; the capture draws immediately after, so the caret is visible on every ordinary run and a 300 ms stall anywhere between the two would blink it out and move the reference by the ten pixels it paints. `FreezeTextCursorMixin` pins it visible - the same freeze `FreezeSpriteAnimationMixin` applies to texture animation, and visible rather than hidden because a freeze holds what the client draws still rather than deciding what it draws.
- The caret has **two forms and the value's length picks which**: vanilla appends a `_` glyph, drawn with a shadow at the text origin, unless the cursor is at the end of a value already at its maximum length, when it fills a one-pixel bar spanning eleven rows instead. The anvil caps its field at 50, so the unnamed subject draws the first and a subject named at that cap draws the second - which is why the named one is at exactly fifty characters and not at a comfortable length.

## Tooltips

- **The call is the client's own `tooltip(...)`, at a fixed origin.** `TooltipSweep`'s extract step is `GuiGraphicsExtractor#tooltip` over the subject's lines as the client's own tooltip components, never the item route, which adds attribute and advanced lines the roster did not ask for. Its positioner places the box at the content origin it is handed, GUI `(12, 12)`: the client's default positioner measures against `guiWidth()`, which reads the hidden window rather than the capture's swapped extent, so it would flip or clamp a wide line against a window nobody sees.
- **The canvas is the whole sprite rect.** The width and height are the client's own measurement, the loop `tooltip(...)` itself runs - the widest line, and every line's height summed less two for a one-line tooltip - and both tooltip sprites are blitted 12 GUI pixels outside that on every side, so the canvas is the measurement plus 24 each way at `GUI_SCALE` and nothing the client draws for a tooltip falls off it.
- **Every subject has a box-alone twin**, `<key>_chrome`, drawn through `TooltipRenderUtil.extractTooltipBackground` at the same measurement: a mover in the twin is the box, and one in the full tooltip alone is the text. The two are drawn in that order at one canvas size, so a pair costs one resize.
- **Four options are asserted, never set**: high contrast, the forced Unicode font and the Japanese glyph variants off, and the language `en_us`. A font option takes effect through a resource reload and the run directory is shared, so the sweep refuses a client running one rather than changing it. The built-in high-contrast pack replaces both tooltip sprites, so a run with it or programmer art selected is refused too.
- **The roster is read by path and parsed by the client's own codec.** `refharness.tooltipRoster` names it, and the harness build defaults that to asset-renderer's tracked `src/visual/resources/lib/minecraft/renderer/sweep/tooltip-roster.json`. Each line is a text component parsed by `ComponentSerialization.CODEC` against the running registries; a line the codec refuses, a roster of another format or two subjects that would write one file refuses the run before its first PNG.
- **A pack run is the same sweep and the same capture** over the roster's section for its packs: `TooltipSweep` constructed for a pack run draws that section into `pack-tooltips/<label>/` beside the reference tree, its sprite ids read through the client's own style-to-sprite helpers. The run, its handshake and the rule its lines keep are in [Probes](Probes.md).
- **No subject is obfuscated.** The client picks an obfuscated glyph off `Font.random`, which nothing seeds, so such a reference would not reproduce and the whole tree's determinism would go with it.
